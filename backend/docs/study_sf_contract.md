## One retained journal and one ingestion endpoint

Proposed next firmware profile: keep LoRa SPI2, SD SPI3, one SD owner, new study directory on an authorized disposable card. Use existing acquisition/formatting and exact 62-byte control capture hooks. Write one JSONL record per capture. No deletion, no global replay ledger, no rotation during the finite trial. Generate a fresh random UUIDv4 per boot, assign a nonzero counter, persist the combined `record_id` with the record. Do not reuse historical 28-bit session/boot tokens as the only identity. Each local append needs a checked outcome; queue drops and incomplete final lines are explicit failures. On restart, retain prior journals; never append after a torn tail or skip it silently. A complete prior prefix can be re-read; new boot uses a new file. Use the existing checkpoint cursor after a file is selected; its two-slot storage adapter still needs integration, or use a conservative replay-from-start implementation for the bounded trial. No untrusted historical F06 metadata is reconstructed into packets.

This candidate defines the wire contract, not an implemented firmware writer or network client. Max 8 records / 16 KiB per request. Per-record ID is `uuidv4:counter`, scoped by recording node. Use one `batch_id` UUIDv4 per request, retain for identical retry in RAM. A restart can create a new batch ID while retaining each record ID. `captured_at` UTC second precision or null, `uptime_ms` uint32. No substitute upload time for event time. All keys in the handler are required; null represents missing readings. Capture weather validity through nulling individual invalid values and preserving state; `micro` null or actual input_valid/state/pattern (not a new forecast). GPS fix false requires null coordinates. `sos` and `cancel` carry exact lowercase hex of 62 on-air bytes, origin and event ID, source local/received. The packet does not authenticate its origin. ACK types not accepted as cloud receipts. Server confirms typed record identity, not rescue acknowledgement.

```json
{"schema_version":1,"batch_id":"bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb","records":[{"record_id":"aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa:1","kind":"gps","recorder_node_id":3,"captured_at":null,"uptime_ms":123,"payload":{"gps_fix":false,"latitude":null,"longitude":null}}]}
```

HTTP 200 only after committed server response, with schema_version, batch_id, recorder_node_id and ordered records [{record_id,status:accepted|duplicate}]. Firmware must verify authenticated HTTPS, matching IDs, batch and node before checkpoint advances. Retry on network/server failure; stop and expose invalid/conflicting record (no silent skip). DB compares semantic JSONB content, not raw JSON formatting. Exact SOS/CANCEL hex preserved. All-or-nothing batch; same ID + changed record rejects the entire batch. The single restricted table references existing vessels.node_id. Original five tables and F06 are untouched. No public reads, no active emergency rows or rescue actions. Dashboard projection will read the study table through an approved authenticated read path, using original capture time, latest valid GPS separately, no fake live status. Aggregate SOS/CANCEL by origin/event, cancellation dominant in either order; do not infer authenticity from recorder credential. Identity reuse after NVS erase is still a boundary; controlled study assumes stable event ID counters, no erase midtrial. Separate uploader authorization and source authenticity. All records are study observations; do not deploy.
