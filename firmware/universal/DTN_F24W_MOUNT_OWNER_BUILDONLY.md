# F24W — Owner-held mount lifecycle preview (DTN only)

Accepted parent: `9ff81cd9a9f7199108584fab9c09c8dd01c54b54` (F24V).
This is a BUILD-ONLY candidate, not an authorized physical SD owner. V001 unavailable; multihop paused. No flash, original V002 SD access, cloud deployment, GitHub push, or relay activation. Scheduled normal LoRa transmissions remain inherited if flashed; this is NOT a globally RF-silent image.

## New lifecycle contract

- One noncopyable/nonmovable `MountOwner` instance privately owns the synthetic backend and two tracked resource slots. A client gets a move-only opaque token (owner address, slot, generation); it never receives a raw resource. Destruction of a token performs no backend I/O and leaves the slot available for controlled drain. Token truthiness means only a syntactic key, not live authorization; the owner must outlive its tokens. Stamp checks prevent stale tokens during that owner's lifetime. The backend is required to have trivial destruction, but that alone is not proof of its internal I/O semantics or absence of aliases.
- Mount requires a preassigned fresh epoch, nonzero media/owner identities and independently supplied authorization/exclusivity/interposition facts. Fresh identity is checked before and after each backend call. These are assumed host witnesses, not authenticated physical evidence. No independent global singleton claim is proven by the class; two separately instantiated owners must be excluded by the eventual integration.
- Only one lane and primary slot at a time. History child and F23D verification slot are ordered before parent close. An explicit planned shutdown refuses new work, closes child before parent, flushes append handles, checks each result and identity, then unmounts. False backend result or witness change latches `Faulted`; uncertain slots remain inventoried; no further call or regrant in that instance. A successful unmount requires the preassigned witness to remain valid through its completion, not to assert the card is still mounted. Mount epochs must increase across planned remounts.
- The busy guard handles same-thread reentry only. It is not an atomic mutex and must not be called concurrently. Backend must be nonthrowing and return false on uncertain outcomes. The model does not establish crash consistency, durable media writes, checked partial transfer semantics, EOF vs failure discrimination, or correct path allowlisting. Higher-level SOS/session rules and future checked backend must supply those. A failed/ambiguous open or close deliberately quarantines rather than retrying.

## Firmware wiring and limits

F24W selects `DenyMountFacade<File>` at the existing `interposedSD` logger seam. The facade contains only `MountOwner<NeverBackend,DenyWitness>`. `begin` and `end` cannot grant authority; metadata operations deny and `open` returns only a default empty Arduino File. F24O/R still use their existing denied witnesses; their positive data operations have NOT migrated to the token model. No actual SD backend or global all-callsite interposition exists. F24V and earlier profiles retain their old code. Independent probe forbidden by compile guard. F23D evidence, fleet, relay, GPIO remain OFF through inherited flags. Actual installed Arduino FS.cpp negative lifetime regression remains in test suite. Existing raw Arduino File implicit cleanup hazard persists outside the permanently denied seam.
